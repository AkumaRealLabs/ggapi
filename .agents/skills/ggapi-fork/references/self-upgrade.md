# ggapi-fork 自升级策略（可控自治）

目标：**能自己变好**，但**不能随便改规矩**。  
本 skill 可以在明确触发下改进自身文件；所有改动仍服从仓库 git 规则（分支 → PR → main），且 **`docs/fork/*` 永远优先于 skill 正文**。

---

## 1. 真相源优先级（冲突时）

| 优先级 | 来源 | 角色 |
|--------|------|------|
| 1（最高） | `docs/fork/*.md` + `AGENTS.md` 二开/治理段落 | 人类约定的流程真相 |
| 2 | 本 skill（`SKILL.md` + `references/*`） | 执行级教练，可跟进文档 |
| 3 | 会话里的临时判断 | 仅当次有效，**不得**静默写进 skill |

规则：

- skill 与 `docs/fork/*` 冲突 → **先按文档指导用户**，再按本策略**提议/修正 skill**（不得改文档去迁就 skill，除非用户明确要求改 SOP）。
- 不得发明文档里不存在的「新流程」再写进 skill 当既成事实；若需新流程，先改 `docs/fork/`，再升 skill。

---

## 2. 变更分级

| 级别 | 名称 | 例子 | 是否可自动改文件 | 是否必须先问用户 |
|------|------|------|------------------|------------------|
| **L0** | 诊断-only | 发现过时链接、缺模式，仅口头说明 | 否 | 否（可提示「可升级」） |
| **L1** | 安全修补 | 错别字、坏链接、与已合并 `docs/fork` 对齐的措辞、补交叉引用、补刚踩过的排障条目（不改规则） | 是（见 §4 触发） | **改文件前简短说明意图**；commit/push/PR 仍要用户点头 |
| **L2** | 能力扩展 | 新 Mode、新检查清单段、新决策表、补 workflow 步骤 | 仅在用户授权「升级 skill / Mode I」或明确「把这个记进 skill」后 | **是**（方案 → 确认 → 再改） |
| **L3** | 规则/安全面 | 改 Hard rules、放宽 main/push/upstream、改品牌/计费红线、改默认语言策略、大段重写 SKILL | 否（禁止静默） | **必须**；且应用独立 `docs/` 分支 + PR 说明「规则变更」 |

**乱升级的典型样子（禁止）：**

- 做业务功能时顺手「优化」整份 SKILL  
- 未对照 `docs/fork` 就重写流程  
- 把更松的安全策略写进 skill  
- 不写 changelog / 不标级别就大改  
- 自动 commit、自动 push、自动合 PR  
- 把 skill 升级和无关业务塞进同一个 PR（除非用户明确要求打包）

---

## 3. 何时「自主」升级（允许主动）

Agent **应当主动**进入升级评估（至少 L0 提示，符合条件则走 L1/L2）当：

1. **文档漂移**：`docs/fork/*` 或 `AGENTS.md` 二开段已更新，skill 仍教旧步骤。  
2. **实战缺口**：本次会话按 skill 执行失败，根因是 skill 缺步骤/错命令，且已用正确做法解决。  
3. **用户明确要求**：`升级 skill`、`改进 ggapi-fork`、`Mode I`、`把这个写进教练`。  
4. **自检命令**（用户跑 `/ggapi-fork 自检`）：对照文档与 skill，输出差距表。

Agent **不得**主动升级当：

- 只是文风偏好、中英混排审美、emoji 多少  
- 与当前用户任务无关的「我想到可以更好」  
- 想缩小/绕过 Hard rules  
- 上游 new-api 行为变化但尚未反映到 `docs/fork` 或团队约定（先更新文档或清单，再升 skill）  
- 同一会话已做过一次 L2+ 升级且用户未再要求（避免连环改）

---

## 4. 自动改文件的闸门（L1）

仅当 **全部** 满足才可直接改 skill 文件（仍不自动 commit）：

1. 变更可归类为 **L1**  
2. 能指出依据：具体 `docs/fork/...` 段落，或本会话刚验证过的命令/结论  
3. Diff 预期 **小而可审**（经验：单次 < ~80 行净逻辑变更；更大则升为 L2 先方案）  
4. 不触及 Hard rules / 安全红线 / 默认中文策略的削弱  
5. 改前用中文 **一句话** 告知：「将做 L1 自升级：…」；用户若说停则停  
6. 改后展示 **变更摘要**（文件列表 + 级别 + 原因），并更新 `references/CHANGELOG.md`  
7. **不** `git commit` / `push` / 开 PR，除非用户明确说提交/推送/开 PR  

若用户说「以后 L1 都不用问直接改」：仍须遵守 1–4、6–7；「一句话告知」可保留为事后摘要，但 commit 权限不自动放开。

## 5. L2/L3 标准流程（Mode I）

```text
发现缺口 / 用户要求升级
        │
        ▼
  对照 docs/fork + 当前 skill，写「升级方案」
  （级别、改哪些文件、不改什么、是否要先改 docs/fork）
        │
        ▼
  用户确认方案（L2/L3 必须）
        │
        ▼
  git: 从最新 main 开 docs/ggapi-fork-* 分支
        │
        ▼
  实施编辑 + CHANGELOG +（若行为变）必要时改 docs/fork
        │
        ▼
  自检清单（§7）
        │
        ▼
  用户说提交 → commit →（可选）push + PR
```

L3 额外：

- PR 标题标明 `skill(rules):` 或说明「硬规则变更」  
- 不得与业务 feat 混 PR  

---

## 6. 版本与 changelog

- `SKILL.md` frontmatter 维护 `metadata.skill_version`（semver）  
- 每次合入 main 的 skill 变更必须在 `references/CHANGELOG.md` 追加一条  

| 版本位 | 何时加 |
|--------|--------|
| patch (x.y.**Z**) | L1：对齐文档、排障条目、错链 |
| minor (x.**Y**.0) | L2：新 Mode/清单/工作流能力 |
| major (**X**.0.0) | L3：Hard rules 或默认安全/治理语义变化 |

---

## 7. 升级后自检清单

- [ ] 与 `docs/fork/README.md` / `branch-and-sync-sop.md` / `diff-inventory.md` 无矛盾  
- [ ] Mode router 与 `workflows.md` 章节仍对得上  
- [ ] Hard rules 未被削弱（push 仅 origin、禁直推 main、品牌、计费红线）  
- [ ] 中文教练语言策略仍在  
- [ ] 未引入「自动 commit/push/merge」类权限  
- [ ] CHANGELOG 已写；`skill_version` 已 bump  
- [ ] 若流程真相变了：先/同时更新了 `docs/fork`，不是只改 skill  
- [ ] GG-002 仍准确；若 skill 职责大变，更新差异清单摘要  

---

## 8. 对用户的固定话术

提议升级时：

```text
当前模式: I（skill 自升级）
级别: L1/L2/L3
原因: …
拟改文件: …
不会改: Hard rules / 自动推送 / …
下一步: 请回复「按方案改」或调整范围
```

L1 已直接修补后：

```text
已做 L1 自升级（未提交）: …
请查看 diff；要入库请说「提交」
```

## 9. 与日常模式的关系

| 场景 | 行为 |
|------|------|
| 正在 Mode B/C/D 办事 | 默认 **不** 改 skill；最多 L0 记一笔「结束后可升级」 |
| 办事中 skill 明显错且阻塞 | 先给出正确步骤完成用户目标；结束后提议 L1/L2，不中途大改文件（除非 L1 且用户同意「先修好教练再继续」） |
| 用户只要业务结果 | 不主动展开 Mode I |
| 用户说「顺便把 skill 也改了」 | 可同会话做，但 **单独 commit** 优先于和业务混 commit |

---

## 10. 禁止写入 skill 的内容

- 密钥、token、生产地址、客户名录  
- 未在文档落地的「口头临时流程」  
- 弱化审查/绕过 PR/允许 push upstream 的「方便写法」  
- 与 AGENTS 计费/三库/JSON 规范冲突的捷径
